# GibFlow BountyOps

Terminal-first tooling for turning a GitHub Issue into a reviewable Gibwork bounty plan.

## What it does

GibFlow BountyOps focuses on the maintainer/developer workflow before a bounty is created:

`GitHub Issue -> normalize -> validate -> Gibwork SDK task input -> dry-run`

The project is intentionally **terminal-first**. There is no custom web dashboard to maintain.

### Current features

- Fetch a GitHub Issue through the GitHub REST API.
- Convert issue metadata into a deterministic `BountyPlan`.
- Carry GitHub labels into bounded Gibwork tags.
- Validate title, source URL, reward amount, and basic plan integrity.
- Convert the plan to the task input shape used by `@gibwork/sdk`.
- Run a safe dry-run that never signs or broadcasts a transaction.
- TypeScript checks and unit-style tests for the planner/validator boundary.
- Designed to compose with the official Gibwork CLI/MCP tooling rather than replacing it.

## Why this is useful

Creating a bounty is more than copying an issue into another interface. Maintainers need to review scope, reward, source traceability, and acceptance criteria first. GibFlow makes that review step reproducible from the terminal and leaves the final financial action behind an explicit Gibwork boundary.

## Requirements

- Node.js 22+
- npm

The current Gibwork SDK release also requires Node.js 22 or newer.

## Install

```bash
npm install
```

## Run the deterministic demo

```bash
npm run demo
```

The demo uses a local fixture. It does not contact GitHub, does not require a wallet, and does not create a real bounty.

## Run against a GitHub Issue

```bash
npm run gibflow -- --repo owner/repository --issue 42 --amount 25
```

The command fetches the issue, generates a plan, validates it, and prints the corresponding Gibwork SDK task input in **dry-run mode**.

No private key is requested by this workflow.

## Verify the project

```bash
npm run check
npm test
```

## Gibwork integration boundary

GibFlow depends on the official `@gibwork/sdk` package. The adapter in `src/gibwork.ts` maps the internal plan to the SDK's `tasks.create` input shape while keeping the default workflow side-effect free.

For live Gibwork operations, the official Gibwork SDK/CLI remains responsible for wallet authentication, transaction preparation, signing, and submission. This repository does not embed a private key and does not claim that the dry-run created an on-chain bounty.

The official Gibwork CLI also provides MCP support. GibFlow is intended to sit upstream of that execution layer: an agent or maintainer can generate and review a plan here, then use the official Gibwork tooling when a real operation is intentionally authorized.

## Architecture

```text
GitHub REST API
      |
      v
  GitHubIssue
      |
      v
   Planner ---------> BountyPlan
                         |
                         v
                    Validator
                         |
                         v
               Gibwork SDK adapter
                         |
                         v
                    Dry-run JSON
```

## Security model

- Dry-run is the default.
- No private key is stored in the repository.
- No transaction signature is generated by the demo.
- No claim of payout, escrow creation, or on-chain settlement is made by the demo.
- A maintainer should review the generated plan before any live financial operation.

## Hackathon scope

This project is a developer-tool workflow for the Gibwork Developer Hackathon. The differentiator is the terminal-first GitHub Issue -> bounty planning layer, with explicit validation and a safe execution boundary around the official Gibwork SDK.

## Limitations

The current version does not automatically create or fund live bounties. It deliberately stops at a validated, SDK-compatible dry-run. This keeps the demo reproducible and prevents accidental signing or spending.

## Roadmap

- Add richer acceptance-criteria extraction from GitHub Issue templates.
- Add optional MCP-facing planning tools for AI coding agents.
- Add configurable policy checks for reward caps, labels, deadlines, and repository allowlists.
- Add an explicit, separately documented live adapter only when the operator intentionally enables it.
